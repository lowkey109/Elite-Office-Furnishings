STAGE 1 — BUILD THE CORE NEXORA LOOP ENGINE
==================================================

Create a real reusable Nexora loop service.

REQUIREMENTS:
1. Create a dedicated loop/orchestrator service, for example:
   - `server/services/nexoraLoop.ts`
   or equivalent existing service location

2. Centralize all Nexora execution through one function, such as:
   - `runNexoraCycle(trigger: "manual" | "auto")`

3. This function must:
   - prevent concurrent duplicate runs
   - set running state
   - capture startedAt and finishedAt
   - call the existing `runNexoraEngine()`
   - persist every run to the existing `nexoraRuns` table
   - store whether the run was manual or automatic if schema supports it
   - return a stable JSON-safe result
   - gracefully handle errors
   - always reset lock state in `finally`

4. Keep or improve existing Nexora memory state:
   - running
   - status
   - lastStartedAt
   - lastFinishedAt
   - lastMessage

5. Preserve existing working Nexora endpoints where possible, but route them through the new loop engine instead of ad hoc logic.

6. If needed, extend `nexoraRuns` schema to support:
   - triggerType ("manual" | "auto")
   - skipped flag
   - skippedReason
   But only if done cleanly and consistently.

7. Ensure all imports are normalized.
8. Ensure no duplicate route logic remains.
9. Ensure TypeScript compiles.

STAGE 2 — ADD THE SELF-RUNNING SCHEDULER + CONTROL API
==================================================

Once the core loop engine is complete, add real autonomous scheduling.

REQUIREMENTS:
1. Add a scheduler that starts Nexora automatically on a configurable interval.

2. Default interval:
   - 30 minutes
   unless a better existing platform convention already exists.

3. The loop must:
   - start on server boot if enabled
   - not create duplicate timers
   - respect the run lock
   - skip if a run is already active
   - log each scheduled run attempt clearly

4. Create loop control endpoints, for example:
   - `GET /api/nexora/loop/status`
   - `POST /api/nexora/loop/start`
   - `POST /api/nexora/loop/stop`
   - `PATCH /api/nexora/loop/config`
   - optional `POST /api/nexora/loop/run-now`

5. `GET /api/nexora/loop/status` must return real state such as:
   - enabled
   - running
   - intervalMs
   - nextRunAt
   - lastStartedAt
   - lastFinishedAt
   - lastMessage
   - status

6. If using only in-memory scheduling for now, clearly document that limitation.
7. Do not fake a persistent scheduler if one does not exist yet.
8. If an existing persistent job system already exists in the codebase, prefer integrating with it instead of creating a second scheduler.
9. If the persistent system is not production-ready yet, use a clean in-memory scheduler now and document that it should later move to persistent job locking.

STAGE 2 DELIVERABLES:

- control/status API works

- real state reporting
