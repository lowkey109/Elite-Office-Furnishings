SECTION 3 — PRODUCTION DESIGN PRINCIPLES
==================================================

The system must follow these principles:

1. Idempotency first
   The same logical email must be treated as one action, even if the code path is triggered multiple times.

2. Database-enforced safety
   Protection must be enforced in persistent storage, not just in memory.

3. Write-before-send discipline
   A send attempt must be recorded before or atomically with send execution.

4. Explicit campaign identity
   Every outreach must belong to a defined campaign or outreach type.

5. Per-recipient suppression
   The same company/contact must not be recontacted unintentionally.

6. Concurrency safety
   Two workers/processes/triggers must not be able to send the same email at the same time.

7. Deliverability protection
   Add rate limiting, cooldowns, and suppression controls.

8. Full auditability
   Every decision must be visible: queued, blocked, skipped, sent, failed, suppressed.

SECTION 5 — IDENTITY / DEDUPLICATION RULES
==================================================

This is the most critical part.

For every outbound email, generate a strong identity hash based on a stable logical identity, such as:

identity_hash = hash(
  normalized_company_name +
  normalized_recipient_email +
  campaign_key +
  normalized_subject +
  body_hash
)

OR, if body can vary slightly, define a stricter campaign send identity:

identity_hash = hash(
  normalized_company_name +
  normalized_recipient_email +
  campaign_key
)

Use the stricter form for first-contact suppression.

REQUIRED RULES

- A message with the same identity_hash must not be sent twice unless explicitly overridden by admin
- Add a unique database constraint on identity_hash where appropriate
- Also add company + campaign suppression rules
- Also add recipient + campaign suppression rules
- Also add cooldown logic

SECTION 6 — STATUS MACHINE
==================================================

Every outreach message must move through a strict state machine:

draft
queued
blocked
suppressed
locked
sending
sent
failed
cancelled

Rules:
- only queued messages may be locked for sending
- only locked messages may move to sending
- only sending messages may move to sent or failed
- suppressed/blocked messages must never send
- sent messages must never send again
- failed messages must not resend automatically unless policy allows and idempotency rules remain intact

SECTION 7 — HARD SAFETY RULES
==================================================

Implement all of the following:

1. COMPANY SUPPRESSION
If a company has already received a first-contact outreach for the same campaign, block further first-contact sends.

2. RECIPIENT SUPPRESSION
If a recipient email has already received outreach for the same campaign, block further sends.

3. COOLDOWN WINDOW
No re-send to same company/contact for the same campaign within configurable cooldown days.

4. DAILY RATE LIMIT
Hard cap total sends per day.

5. HOURLY RATE LIMIT
Hard cap total sends per hour.

6. PER-DOMAIN LIMIT
Limit messages to same domain within a configured time window.

7. SAFE MODE
System can queue and audit without sending.

8. MANUAL APPROVAL MODE
Certain campaigns require explicit approval before send.

9. JOB LOCKING
Only one job instance may process a given campaign/job key at a time.

10. PROVIDER FAILURE SAFETY
Provider retry must never bypass idempotency.

SECTION 8 — SCHEDULER / JOB SAFETY
==================================================

The current system may be using in-process timers or repeated triggers.
That is not safe enough.

Rebuild job execution with persistent job locking.

Required protections:
- acquire job lock before processing
- if lock exists and is fresh, skip run
- if stale lock exists, mark stale and safely recover
- record started_at and completed_at
- record job outcome and errors
- no overlapping sends for same job type/campaign

If the system still uses a scheduler, it must call a single safe job runner that is idempotent.

SECTION 9 — SEND PIPELINE
==================================================

Implement the send pipeline in this order:

1. receive intent to send
2. normalize company/contact/campaign identity
3. check suppression rules
4. check dedupe rules
5. check cooldown
6. check rate limits
7. create or fetch existing message by identity_hash
8. if already sent / suppressed / blocked, exit safely
9. acquire row-level lock / safe processing lock
10. move to locked
11. move to sending
12. call email provider
13. persist provider result
14. move to sent or failed
15. write audit event

At no point should the system ever "just call sendEmail()" without full gating.
